# 无相（Wuxiang）项目书

> **首页结论：M0 不是“真实 AI MVP”。** M0 只验证可运行的 SDK 工程基础和本地 UI 闭环；只有 M1 接入真实模型生成 schema、服务端保管 key、有限校验修复、取消/超时和文本 fallback 后，才可称为 AI 闭环。旅行示例只是闭环演示，不是旅游业务定位。

## 项目定位

无相探索一种 Agent Interface Runtime：应用保留稳定的 shell，由 Agent 按任务产生可验证的动态 surface；用户操作以事件回到 Agent。目标是让开发者少写任务交互代码，让用户更快完成任务。视觉变化数量本身不是成功标准。

当前状态为新仓库、M0 建设期。Node `24.4`、npm `10.9.7` 是当前开发环境记录；实现细节和最终 API 以代码、类型和测试为准。

## 四类信息边界

### 用户明确意愿

- 想创造每次由 AI 生成显示和交互 UI 的产品“无相”，并讨论过 Wuxiang 与 Morph 命名。
- 需要判断开源或闭源的商业化路径。

### 讨论中的 GPT 建议

- 可将产品描述为 Wuxiang Agent Interface Runtime：固定 shell + 动态 surface。
- 采用声明式协议、注册组件渲染、interaction event 回 Agent；按任务选择 text、UI 或 text+UI。
- 先组合基础组件和布局，必要时再考虑沙箱新组件；`Morph` 可作为能力名。
- 可能采用开源核心、Cloud、Enterprise、可选 Intelligence，Marketplace 放到更后面。

这些建议不是市场事实、可行性证明或收入预测。

### 本期明确决策

- M0 交付 npm workspaces + TypeScript 的 `packages/protocol`、`runtime`、`react`，以及 `examples/playground` 本地 SDK 演示。
- 本期从能运行的 SDK 工程基础开始，不先做完整云产品。
- M0 内部协议版本为 `0.1`，核心语义包含 `surfaceId`、`revision`、节点树和 action allowlist；具体字段和函数签名以代码核对。
- runtime 框架无关，严格校验、原子 replace、拒绝过期 event、有限内存历史；只读 replay 不执行副作用。
- React 首期只允许九类白名单组件：`Text`、`Card`、`Stack`、`Button`、`Input`、`Select`、`Form`、`Table`、`Progress`。
- playground 用旅行偏好 mock 表单 → 结果 → 修改且保留值，便于展示闭环；不接真实预订、模型、云或第三方服务。
- 所有包暂为 `private`、`UNLICENSED`；不发布、不部署。是否 Apache-2.0/MIT 待 ADR 评估后决定。

### 待验证假设

- 对有复杂 Agent 交互的独立开发者和小团队，声明式动态 surface 能减少任务交互代码。
- 一旦接入，用户完成任务会比传统 chat/control 更快或错误更少。
- 开发者能在 5–10 分钟内完成首次接入（目标，不是已有成果）。
- 基础校验和自托管应保持低门槛，云托管与组织治理可能形成付费边界；价格、付费意愿和市场规模都未验证。

## 用户、问题与价值

目标用户是需要多步骤、强表单或结果操作的 Agent 产品独立开发者和小团队。今天他们往往要手写状态、校验、事件分发、结果展示和回填逻辑；纯聊天又让用户在多轮追问中重复确认。无相希望把任务交互的共同部分收敛为声明式 surface、受限 renderer 和可追踪事件，让开发者主要描述任务能力，让用户在一次可见的流程中完成输入、结果和修改。

首个场景是旅行偏好 mock 流程：填写偏好、查看结果、修改输入并保留已有值。它只用来验证“动态 UI + 事件 + 状态回填”的闭环，不代表无相要做旅游产品。

## 首期边界

M0 必须能让本地开发者安装 workspace、构造一个合法 surface、渲染九类组件、触发 allowlist 内 action、拒绝坏输入和过期事件，并从只读历史重放状态。M0 不包括真实模型、服务端 API、云托管、鉴权、真实预订、任意代码执行、插件市场、生产可用性承诺或跨生态兼容承诺。

## 竞争与生态边界

- [A2UI](https://a2ui.org/) 提供声明式 Agent UI 协议和组件 catalog，是需要评估映射/复用的邻近项目；无相 M0 的 `0.1` 只是内部试验协议，不声称创建新标准或已兼容 A2UI。
- [MCP Apps](https://modelcontextprotocol.io/extensions/apps/overview) 的交互模式是 HTML 沙箱 iframe + JSON-RPC/postMessage；它不是把无相 JSON 换几个字段就能兼容的协议，适配应另行设计。
- [assistant-ui](https://www.assistant-ui.com/pricing) 的核心 React/TypeScript 库与可选 hosted persistence 属于相邻的 UI/Cloud 组合；无相的试验重点是任务 surface 与受限 runtime。
- AG-UI、LangGraph、AI SDK 等适配保持为后续待核验事项，当前不宣称已支持。

## 成功判断与测量

没有虚构基线；首期先记录方法和基线，再比较传统 chat/control。

| 指标 | 口径 | 首期目标/状态 |
| --- | --- | --- |
| 接入耗时 | 从干净仓库开始到首次渲染并触发一个合法交互的分钟数；记录每位开发者和中位数 | 目标 5–10 分钟；待实测 |
| 任务完成率 | 启动任务后达到预先定义结果的会话数 ÷ 全部启动会话数；另报用户主动取消数/率，不用排除取消来抬高完成率 | 无基线，M1 后对比 chat/control |
| 错误率 | 每个任务中用户纠正、无效提交或回退次数 ÷ 任务启动数；需固定事件分类 | 无基线，M1 后对比 |
| 校验成功率 | 首次生成通过 schema/白名单校验的 surface 数 ÷ 首次生成 surface 数；另报有限修复后通过率 | M0 本地基线；M1 才有真实模型值 |
| 时延 | 从提交请求到首次可交互 surface 的 p50/p95；取消、超时和模型等待单独计数 | 无基线；M1 记录 |
| 单任务成本 | 模型 token、服务端计算和相关托管成本 ÷ 成功完成任务数 | 无基线；价格待验证 |

验证实验：邀请 5 位目标开发者，用同一旅行偏好任务尝试接入，记录安装到首次交互的时间、遇到的手写代码量和摩擦点；随后以传统 chat/control 做小样本对照，观察完成率、错误率和耗时。样本小，只用于发现问题，不用于市场结论。

## 商业边界与命名

基础协议校验和自托管不应成为收费限制；云托管、组织治理、审计和规模化运维可以作为潜在付费边界。价格、授权、客户类型和收入预测尚未验证。M0 暂不选 Apache-2.0/MIT，也不发布 npm 包。

“Wuxiang/无相”是当前项目名；“Morph”保留为未来能力名候选。命名不代表产品已经完成市场定位。

## 关键风险

- 动态 UI 增加模型输出和状态复杂度，必须先守住 schema、组件和 action 边界。
- 纯内部协议可能造成无谓生态竞争；M1 前必须评估 A2UI 映射/复用。
- 旅行 demo 容易被误读成垂直业务；所有演示和指标都围绕任务交互能力表述。
- 实际接入时长、任务收益、模型成本和付费意愿均未知，需实验而非推断。

# M1 试用与评估方案

本文件提供执行脚本和空白记录表，不是已完成的用户研究报告。当前 `OPENAI_API_KEY` 与 `OPENAI_MODEL` 尚未配置；真实模型调用及开发者实验均无结果可报告。单元测试、mock 演示或 SDK build 不能记成真实模型成功率或用户收益。

## 验证问题

1. 开发者是否能少写任务表单、结果展示、字段回填和事件协调代码？
2. 同一任务中，AI surface 相对传统 chat/control 是否改变完成率、耗时和错误数？
3. 模型输出首次通过校验的比例、有限修复后的通过比例、文本 fallback 原因、时延和 token 用量分别是多少？

核心价值假设是“开发者少写任务交互代码、用户更快完成任务”，不以生成了多少种不同 UI 为成功指标。

## 试用准备

主持人准备：

- 使用同一版本提交，记录 git commit、Node/npm 版本、OS、浏览器、模型名和实验日期。
- 在本地服务端配置 `OPENAI_API_KEY` 与 `OPENAI_MODEL`；当前环境两者均未设置。密钥放在本地 `.env`，不要发到聊天、Issue、表格或截图，不得放入 `VITE_` 前缀变量。
- 开始前确认 `/api/agent/status` 的 `configured` 值；不要记录或展示密钥本身。
- 准备 5 位目标开发者（有复杂 Agent 交互需求的独立开发者/小团队）；本计划未招募任何参与者。
- 为每位参与者分配随机编号；记录最少必要过程数据，避免采集真实旅行、身份或支付资料。

若缺少环境变量、调用被取消或上游失败，记录为配置/失败事件，不得伪装成 fallback 成功或排除出分母。若使用共享 API key 预算，事先设定额度并告知参与者。

## 开发者接入计时脚本

对每位开发者单独执行并计时：

1. 从干净 clone 开始，给同一条起始任务：“在现有 React 应用中接入动态表单，收集两个旅行偏好字段，提交后展示一个结果，并支持修改保留值。”旅行内容只作任务载体。
2. 允许查看 README、`docs/API.md` 和项目源码；记录查阅、问题、复制代码段、手写的状态/表单/event/校验代码行及求助次数。
3. 从第一次打开仓库/启动计时开始，到通过预先准备的验收为止：页面能打开；合法 surface 渲染；一次 action 到达 handler；结果展示；修改时旧值保留；坏 surface 被拒绝。记录结束时间和验收失败项。
4. 记录主动放弃或外部中断，仍保留该名参与者和实际耗时/状态，不静默排除。
5. 完成后用固定问题收集阻力：“最难理解的 API 是什么？”、“相比手写 UI/聊天流程少了什么、多了什么？”、“你会在什么任务中试用？”、“哪条限制阻止你接入？”不要引导参与者给好评。

接入耗时从开始到达到全部验收条件的分钟数；报告每位参与者、成功/未完成状态、中位数和范围。另报手写任务交互代码量及摩擦主题。样本为 5 名，只作为小样本问题发现，不得外推市场规模或普遍接入时间。

## 用户任务对照脚本

同一参与者分别使用 dynamic-surface 与传统 chat/control 完成同一任务；初始信息、完成条件和主持人口径保持一致。轮换 AB/BA 顺序，降低练习顺序影响。

任务：“为一次假想周末旅行给出偏好（日期、预算、同行者等）；查看建议；修改预算或同行者后再提交；说出最终保留的选择。”只用虚构数据，不连接真实预订或付款。

逐项记录：

1. `started`：用户看到任务并开始输入/发送。
2. `completed`：用户明确确认最终结果满足预设完成条件，且所需字段齐全。
3. `user_cancelled`：用户主动结束；系统错误、超时或主持人终止不得误标为用户取消。其他未完成分别标 `interrupted` 或 `system_failed`。
4. `correction`：用户因误解、缺项、错误值或结果不符而主动纠正；同一任务可多次。
5. `invalid_submit`：表单/系统拒绝一次用户认为自己已完成的提交；两种模式均使用预先固定的判定规则。
6. `backtrack`：完成前返回修改已确认步骤；另记是否为任务要求的正常修改。
7. `elapsed_seconds`：从 `started` 到完成、用户取消或实验结束；系统请求时延另记。

## 指标口径

| 指标 | 分子 / 分母 | 报告方式 |
| --- | --- | --- |
| 任务完成率 | 达到预定义完成条件的任务数 ÷ 全部已启动任务数 | 所有启动都留在分母；另报主动取消率、系统失败率和中断率。 |
| 用户主动取消率 | `user_cancelled` 数 ÷ 全部已启动任务数 | 不把服务端取消、超时或程序错误记为用户主动取消。 |
| 任务错误率 | 发生至少一次预定义纠正或无效提交的任务数 ÷ 全部已启动任务数 | 同时报每任务纠正/无效提交次数分布，并单列按要求完成的正常修改。 |
| 首次校验成功率 | 首次模型 UI 响应通过 `parseSurface` 的数 ÷ 全部首次模型 UI 响应数 | text mode 单独报告；请求级失败另报。 |
| 修复后通过率 | 一次修复响应通过 `parseSurface` 的数 ÷ 实际发起修复的响应数 | 同时报修复发起率、repair token 与时延。 |
| 首次可交互时延 | 从用户提交到首个可交互 surface 或 text 显示的秒数 | 报 p50、p95；区分 UI、text、repair 后成功和 fallback。 |
| 生成成功率 | 成功到达可显示 UI 或有效 text 的请求数 ÷ 全部生成请求数 | cancelled、timeout、provider/schema error 分别报告；不能只报 success。 |
| 接入耗时 | 干净 clone 开始至通过全部开发者验收的分钟数 | 报参与者状态、中位数和范围；未完成仍列出。 |
| 交互代码量 | 为完成任务实际新增/修改的任务级 UI、状态、事件、校验代码行数 | 需有统一统计规则和相同工程基线；不能只对某一组计生成代码或基础工程。 |

五位参与者只提供小样本可用性信号。先描述方向、分布和摩擦，不做显著性、因果或市场判断；比较两种模式时，报告顺序和未完成任务。

## 报告模板

试用报告写明实现 commit、模型/环境、招募及缺失数据、所有分母、指标原始计数和分布、失败样本、参与者摩擦主题及下一步决策。先记录实际结果再计算比例；不得只报告成功请求、排除主动取消后计算完成率，或把代码测试数据当真实模型输出。对外分享前去标识化，并移除 prompt 中可能含有的个人信息。
